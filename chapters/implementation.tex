\label{chap:implementation}
This chapter describes the tool that realises the design of Chapter~\ref{chap:design}, thereby completing, together with that chapter, the answer to Research Question~2. The tool is a contribution of this thesis, but it is not its subject: it is the instrument through which the design is evaluated. The chapter therefore records the architecture and the components that matter for reproducing the tool and for trusting the evaluation, and refers back to Chapter~\ref{chap:design} for the interface behaviour it realises rather than restating it. Alongside the study planner, a small questionnaire application was built to conduct the evaluation sessions; it is described briefly in Section~\ref{sec:impl-userstudy}.

\section{System Overview}
\label{sec:impl-overview}

The study planner is a single-page web client backed by a stateless HTTP service and a relational database (Figure~\ref{fig:impl-architecture}). The client is a React\footnote{\url{https://react.dev}, version~18.3.1.} application built with Vite\footnote{\url{https://vite.dev}, version~5.4.20.}, and renders both the graph and the Table View on a single interactive canvas provided by React~Flow\footnote{\url{https://reactflow.dev}, version~11.11.4.}. The service is written in Python with FastAPI\footnote{\url{https://fastapi.tiangolo.com}.} and encapsulates catalogue access, plan persistence, curriculum-compliance checking, and recommendation. Data is stored in PostgreSQL\footnote{\url{https://www.postgresql.org}, version~16.}. This separation places presentation on the client, logic on the server, and data in the database, which is the arrangement the requirements already imply, with interface features (for example the graph-to-table workflow, Feature~\ref{feat:004}) kept distinct from the logic-heavy compliance (Feature~\ref{feat:003}) and recommendation (Feature~\ref{feat:007}) features.

\section{Frontend}
\label{sec:impl-frontend}

The client realises the interface designed in Chapter~\ref{chap:design} and is the larger of the two applications. It is organised in three layers, each depending only on the one below it (Figure~\ref{fig:impl-frontend-layers}), and this section describes them from the bottom up: first the model the plan is held in, then the feature modules built on it, then what those modules present to the student, and finally how an edit travels through them.

\subsection{The Plan Model}
\label{sec:impl-plan-model}

The plan has a single authoritative representation, and the Graph View and the Table View are two projections of it. Switching view changes how the plan is drawn, never which plan is described, and persistence, the Dashboard, compliance feedback and recommendations are all derived from the same model.

That model is a reducer: a function from the current plan and a described change to the next plan, holding no framework, no clock and no input or output of its own. Placing a course, moving it, parking it, marking it complete and applying a prebuilt plan are transitions of this function, so each can be exercised by calling it rather than by rendering the interface around it. The reducer sits in a domain layer together with the term and lane rules, the lane geometry, the graph filters and the prebuilt-plan builders. That layer depends on no framework and on no other layer, which is what allows the planning rules to be tested without a browser.

\subsection{Feature Modules}
\label{sec:impl-frontend-features}

Above the domain layer, the client is divided by feature rather than by technical kind. Each of the profile, the catalogue, the Dashboard, the Recommendation Panel, the onboarding tour, the prebuilt plans, the compliance feedback and the planning canvas is a module holding its own state, its own effects and the components that render it; the screen is assembled from them. A module may depend on the domain layer and on no other module, so a change to one feature cannot reach another except through the plan.

\subsection{How an Edit Travels}
\label{sec:impl-edit-flow}

Edits follow one direction (Figure~\ref{fig:impl-edit-flow}). A drag or a button dispatches a transition that rewrites the plan; from there, two independent consequences follow. Immediately, a set of pure layout functions reflow the affected lanes or graph columns and the active view re-renders. Separately, and off that render path, the plan is persisted and the compliance and recommendation endpoints are consulted, with their results feeding the derived Dashboard and the transient feedback banners. Because this second step is debounced rather than triggered on every keystroke, the rapid, exploratory replanning the tool is built for stays responsive. The four-state course lifecycle designed in Section~\ref{sec:lifecycle} needs no separate state-machine object: each course carries its state on the plan, the transitions are the reducer's own, and the context-sensitive buttons are derived at render time so only valid transitions are offered. Filtering the graph is handled by a self-contained module that matches courses against the active filters and then keeps every ancestor of a match, so a course is never hidden merely because an intermediate module was filtered out (Section~\ref{sec:graph-spatial}).

One qualification applies to this account, and it bounds the single authoritative model of Section~\ref{sec:impl-plan-model} rather than contradicting it: the table's canvas holds each node's coordinates, and a course's horizontal coordinate encodes the semester it occupies, so that one derived value is reconciled in both directions rather than one.
Making the canvas a pure projection of the model, so that reconciliation runs one way only, is the clearest structural improvement the client still admits, and it is taken up in the future work of Chapter~\ref{chap:discussion} (Section~\ref{sec:disc-future}).

\section{Backend}
\label{sec:impl-backend}

Everything above happens in the browser and is lost when it closes. What follows is the half that persists the plan and answers the two questions the client cannot answer for itself, whether a plan is compliant and what to suggest next.
The service is a FastAPI application arranged in three layers (Figure~\ref{fig:impl-backend-components}). As in the client, a layer may use the one below it and not the one above, but the layers themselves are different: where the client separates features from a shared domain, the service separates handling a request from deciding what it means and from reaching storage. A request handler validates its input, calls exactly one use case, and shapes the reply; it holds no rules and no SQL. A use case orchestrates the domain and owns the transaction boundary. A repository holds SQL and nothing else, and every SQL statement in the service is in one. The handlers cover authentication and sessions, catalogue retrieval, plan loading and saving, profile settings, compliance checking, recommendation, and capture of study results, that is the per-session submissions of the questionnaire application (Section~\ref{sec:impl-userstudy}), which are stored as one document per participant. 
The layer boundary that needs stating in words rather than in the figure is the one between a use case and storage. A use case reaches storage through a unit of work: an object that hands it every repository already bound to one connection. A use case therefore never acquires a connection and never names a concrete repository. Two consequences motivate the arrangement. A use case can be exercised against a substitute unit of work, without a database; and the point at which a sequence of statements either all apply or none do is stated in the use case rather than left to whichever repository happens to run first.

When a use case cannot do what was asked, it raises a failure of its own rather than an HTTP error. These failures are named for what went wrong rather than for how they will be reported, for example a programme locked after setup, a start term already fixed, or a profile saved before the setup it depends on. One table maps those names to HTTP status codes, and it is the only place in the service that knows what a status code is.

Two further properties are worth recording. Authentication resolves a user from a session token supplied either as a cookie or as a bearer token, so the deployed client and a local instance authenticate against the same service unchanged. Persistence uses a shared PostgreSQL connection pool with parameterised SQL rather than an object-relational mapper, which keeps the queries the catalogue depends on legible and directly measurable. The two logic-heavy concerns, compliance and recommendation, sit beside the use cases as domain packages of their own; the next two sections describe them.

\subsection{Curriculum Compliance Engine}
\label{sec:impl-compliance}

The Compliance Engine realises the curriculum-rules and feasibility features (Feature~\ref{feat:003}, Feature~\ref{feat:005}). The rules it applies are taken from the two curricula the tool supports, the Bachelor programme in Computer Science and the Master programme in Software Engineering, as published by TU Wien\footnote{\url{https://informatics.tuwien.ac.at/bachelor/curriculum-ue033521.pdf}, \url{https://informatics.tuwien.ac.at/master/curriculum-ue066937.pdf}; the versions in force during this work were used.}. No rule in the engine originates elsewhere.

The Compliance Engine separates the curriculum's own content from the logic that evaluates it. Each programme's regulations are a JSON document in \texttt{app/curriculum/}: the modules and their credit weights, the mapping from course code to module, the introductory-phase course sets, the focus areas and their aliases, the prerequisite pairs, and the thresholds, nine constants for the Bachelor programme and five for the Master. The checker for a programme reads that document once, in its constructor, and holds only the checking, so a curriculum revision is an edit to the document rather than to the code.

The evaluation logic comprises two programme-specific rule sets, resolved dynamically via the programme identifier. These implementations are intentionally distinct, as the structural overlap between the two curricula is minimal. For instance, the Bachelor curriculum enforces a strict introductory phase, the \emph{Studieneingangs- und Orientierungsphase} (\gterm{steop}{StEOP}), absent from the Master programme, while the Master programme introduces a focus-area gating matrix not found in the Bachelor curriculum. Consequently, the two engines share only the external API contract: the request format, the response schema, the entry point, and the calculation of per-semester credit limits. Abstracting the remaining logic into a unified base class was deliberately not attempted: with the two rule sets sharing so little, the common core would have been smaller than the machinery needed to express it, and every programme-specific rule would have reached its data through an indirection that explains nothing. Whether a genuine common core emerges once a third programme is added is a question for future work, and it is the point at which the decision should be revisited.

Upon receiving a study plan, the engine evaluates it through a multi-pass pipeline to produce a single structured result. It first calculates per-semester and per-subject credit aggregates. It then validates these against the curriculum constraints, verifying mandatory module completion, exam-subject minimums, total ECTS targets, per-semester workloads, and sequence recommendations. The evaluation output strictly categorises feedback into two tiers, allowing the interface to guide rather than block the user (Section~\ref{sec:overall-scope}). Hard violations, such as exceeding absolute workload ceilings or breaking hard prerequisites, mark the plan as non-compliant; warnings, such as exceeding a recommended workload or scheduling electives prematurely, serve as advisory notices. In addition to the compliance verdict, the engine returns the calculated statistics required to render the Dashboard, ensuring that the visual interface and the rule engine rely on identical state computations. This same engine is subsequently queried to validate system recommendations, as described in the following section.

\subsection{Recommendation Support}
\label{sec:impl-recommender}
The recommendation component exists to exercise the recommendation \emph{workflow} of the design (Feature~\ref{feat:007}, Feature~\ref{feat:012}), not to advance recommender research. It deliberately combines existing educational-recommender techniques rather than any new method: content-based matching against a student's stated interests and curated course similarities, typical-sequence relationships of the kind sequence-based course recommenders propose~\cite{wong_sequence_2018}, and a \enquote{what other students did} lens modelled on collaborative filtering for elective recommendation~\cite{bhumichitr_recommender_2017}. Each suggestion is accompanied by a short, human-readable reason, and any suggestion that would introduce a new hard violation is filtered out by re-checking it against the Compliance Engine, so recommendations never push a plan out of compliance.
The two content-based channels are implemented as follows. Interest matching compares a student's stated interests against each course's topic list and its description, weighting an explicit topic match above an occurrence in the description and a partial word overlap below both, and normalising the result by the number of interests named, so that naming ten interests and matching one does not score as naming one and matching it. Course similarity infers nothing: it reads curated course-to-course links recorded in the catalogue, each carrying the short justification that is shown to the student as the reason (Figure~\ref{fig:impl-shot-recs}). The two behavioural channels are computed the same way from a cohort of prior-student plans: the peer channel scores a candidate by the share of the cohort whose plan most resembles this one that also holds it, and the follow-on channel by the share of the cohort who took it after a course this student has completed. Both report that share as the reason, and both distinguish a genuine cohort comparison from a fallback to overall popularity when the cohort is too small to support one.

The quality or accuracy of the underlying algorithms is explicitly out of scope for this thesis: the collaborative-filtering lens in particular operates on synthetically generated prior-student histories rather than real interaction data, so it stands in for the workflow a data-driven recommender would support rather than reproducing its performance.

\section{Data Model}
\label{sec:impl-data}

The database models a study programme as a strict hierarchy (Figure~\ref{fig:impl-data-model}): a programme groups exam subjects, each exam subject groups modules, and each module groups courses, so that every course belongs to exactly one module. To avoid expensive relational queries at read time, we pre-assemble the catalogue into a single nested JSON document per programme using a materialised view. The client fetches this entire structure in a single request. A student's own term-availability overrides are merged onto it locally, ensuring the shared data is never mutated. Course-level metadata that evolves independently of the relational schema, such as content descriptors and curated course similarities, is held in a JSONB attributes column on the course entity. Per-user data, including the account, the saved plan, and the recommendation and term profiles, is keyed to the user and kept strictly separate from the shared catalogue. An account holds exactly one plan, since the plan table is keyed on the user and written as an upsert, while the profiles are keyed on the user and the programme, so a student who switches programme keeps a profile for each. One plan per account was sufficient for the study and for the design's own scope, but it prevents a student from holding alternative drafts side by side, which is a limitation the Discussion returns to (Chapter~\ref{chap:discussion}, Section~\ref{sec:disc-future}).

We manage the database schema through automated migration files applied in sequence on start-up, which guarantees a reproducible environment. To support concurrent development without identifier collisions, migrations use timestamp-based naming rather than sequential integers. We also track each migration via a checksum to prevent silent modifications to previously applied scripts. \section{Verification}
\label{sec:impl-verification}

Munzner's nested model attaches its own threat, and so its own form of validation, to each level, and warns that a poor result at one level may in fact be caused by a poor choice at a level inside it~\cite[p.~922]{munzner2009}. The algorithm level is this chapter's, and verifying it here is what allows Chapter~\ref{chap:evaluation} to read a usability result as a statement about the design rather than about a defect underneath it. We focus verification on the Compliance Engine, as both user trust and the evaluation findings depend entirely on its correctness, and verify the system across three levels.
First, a test suite records the engine's exact output across 38 scenarios for both degree programmes, covering empty plans, boundary conditions, and deliberate rule violations. We compare every verdict and statistic field by field to pinpoint specific rule failures. To prevent degenerate test states, the suite automatically fails if the scenarios do not produce a sufficient variety of distinct outputs. We apply this same snapshot strategy to the recommender system across 85 distinct profile and channel configurations.
Second, contract tests verify the API surface. We sanitise dynamic values, such as timestamps and identifiers, to strictly assert that endpoint status codes and response structures remain stable across runs.
Third, end-to-end tests drive a browser against the running stack to simulate the core planning loop. This is necessary to verify the two-way reconciliation between the plan model and the interface canvas (Section~\ref{sec:impl-edit-flow}), which cannot be observed outside a real browser environment.
Standard unit tests cover the remaining components. Client-side tests isolate the domain layer, including the plan reducer and graph filters. Service-side tests cover the curriculum documents, individual recommendation channels, catalogue queries, and database migration integrity. A continuous integration pipeline runs this entire suite alongside strict type checks on every change.
This heavy reliance on recorded verification is effective here because the Compliance Engine is strictly deterministic and the plan model is a pure function of its inputs, guaranteeing stable test outputs for any given state.

\subsection{The Soft-Dependency Edge Layer}
\label{sec:impl-prereq-edges}

The evaluated graph already drew the formal prerequisite pairs the two curricula fix, as a togglable overlay on the containment layout (Chapter~\ref{chap:design}, Section~\ref{sec:graph-ltr}). What it did not draw was the other half of the relation the Compliance Engine holds: the soft, recommended orderings the engine reports as non-blocking Dashboard advisories (Section~\ref{sec:impl-compliance}; Feature~\ref{feat:003}, Req.~3). That asymmetry was a design decision rather than a limit of the data. The overlay was scoped from the outset to the relations the Compliance Engine blocks on, so that an edge in the graph would carry one meaning, this ordering is required, and a student would not have to ask of any given edge whether it was binding. The evaluation showed the cost of that choice: four participants asked for ordering information at the point of placement and did not receive it (E-P44), and no other view offered it either. The layer added afterwards therefore widens the overlay rather than acquiring anything new, drawing the recommended orderings the curricula themselves state, as notes on the prior knowledge a course expects, alongside the pairs they fix.

The layer reuses the mechanism the formal edges already use. The soft pairs, which live as an attribute of each programme's checker class (Section~\ref{sec:impl-compliance}), are now served alongside the catalogue instead of remaining inside the engine, and the graph renders them as a second edge style: dashed where the formal edges are solid, and labelled \emph{recommended before} where the formal edges read \emph{required before}, so the two are told apart on the canvas rather than through a legend. Both kinds answer to one switch in the filter sidebar, which draws them together or not at all, so the overlay can be cleared in a single action, which is what the decluttering requirement asks for (DEP-04). Because both edge types cross the exam-subject bands rather than running along them, they are drawn above the containment layout and are hidden by default; node positions are unchanged, so the spatial memory the design protects (Feature~\ref{feat:013}, Req.~2) survives turning the overlay on and off.

Two limits on this layer should be stated plainly. It was built after the study, so no participant used it and Chapter~\ref{chap:evaluation} carries no evidence about how it is read. And what the switch draws is thin by construction: the relations the curricula fix between two named courses are two advisory pairs in the Bachelor programme and two enforced ones in the Master, a handful of edges over a graph of 84 courses. The expected-knowledge orderings are more numerous, 99 edges in the Bachelor programme and 24 in the Master, but they are never drawn together: they appear around a single node, on request, which is what keeps them from returning the graph to the density the collapse controls exist to manage. Chapter~\ref{chap:discussion} (Section~\ref{sec:disc-future}) takes up what would have to be established before a view of this kind, drawing dependencies and soft dependencies together, could be said to earn its place.

\section{Key Decisions}
\label{sec:impl-decisions}
Four decisions shaped what the evaluation was able to observe, and it is that consequence rather than the rationale already given above that is worth drawing together here.

The single authoritative plan model (Section~\ref{sec:impl-plan-model}) is what made the two-condition design possible at all. Because both views are projections of one plan, turning the graph off removes a projection rather than a data path, so the graph-off condition is the same tool with one surface withdrawn and not a second tool that has to be trusted to behave identically. The substitution result of Chapter~\ref{chap:evaluation} rests on that: the catalogue and the graph could exchange places in the workflow precisely because neither owned the plan.

Holding each programme's regulations apart from the logic that evaluates them (Section~\ref{sec:impl-compliance}) is what let the study use two curricula and one instrument. The Bachelor programme's rules drove every session reported here while the Master's remained available and unchanged, which is why the completion audit can be read as a statement about plans rather than about which rule set happened to be loaded.

The deliberate simplicity of the recommendation component (Section~\ref{sec:impl-recommender}) determined what the recommendation findings can mean. Because the channels combine standard techniques over placeholder data, the study observes how students treat an explainable suggestion rather than how good the suggestions are, and the expertise-moderated pattern the Discussion reports is a finding about the workflow that survives whatever a better ranking would have produced. The same decision is why two channels were inert during the study, which bounds that finding in the opposite direction.

Verifying the Compliance Engine by recording its answers rather than asserting propositions about them (Section~\ref{sec:impl-verification}) is what makes the evaluation's central negative result checkable. When Chapter~\ref{chap:evaluation} reports that the tool certified plans breaching constraints it does not model, that is a statement about the engine's scope and not a suspicion about its correctness, because the recorded corpus shows the engine answering consistently for the rules it does hold. A test suite restating the curriculum as propositions could not have separated those two possibilities, since a misreading of the curriculum would have appeared identically in the rules and in the tests meant to check them.
