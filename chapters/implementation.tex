\label{chap:implementation}
This chapter, together with Chapter~\ref{chap:design}, answers Research Question~2:

\begin{quote}
\textit{How can we design and implement a hybrid interface that combines graph-based visualisation with table-based planning to help students plan their studies and understand curriculum structure and course dependencies, based on those requirements?}
\end{quote}

Chapter~\ref{chap:design} answers the design half; this chapter describes the tool that realises it. The tool is a contribution of this thesis, but it is not its subject: it is the instrument through which the design is evaluated. The chapter therefore records the architecture and the components that matter for reproducing the tool and for trusting the evaluation, and refers back to Chapter~\ref{chap:design} for the interface behaviour it realises rather than restating it. Alongside the study planner, a small questionnaire application was built to conduct the evaluation sessions; it is described briefly in Section~\ref{sec:impl-userstudy}.

\section{System Overview}
\label{sec:impl-overview}

The study planner is a single-page web client backed by a stateless HTTP service and a relational database (Figure~\ref{fig:impl-architecture}). The client is a React\footnote{\url{https://react.dev}, version~18.3.1.} application built with Vite\footnote{\url{https://vite.dev}, version~5.4.20.}, and renders both the graph and the Table View on a single interactive canvas provided by React~Flow\footnote{\url{https://reactflow.dev}, version~11.11.4.}. The service is written in Python with FastAPI\footnote{\url{https://fastapi.tiangolo.com}.} and encapsulates catalogue access, plan persistence, curriculum-compliance checking, and recommendation. Data is stored in PostgreSQL\footnote{\url{https://www.postgresql.org}, version~16.}. This separation places presentation on the client, logic on the server, and data in the database, which is the arrangement the requirements already imply, with interface features (for example the graph-to-table workflow, Feature~\ref{feat:004}) kept distinct from the logic-heavy compliance (Feature~\ref{feat:003}) and recommendation (Feature~\ref{feat:007}) features.

In deployment, the client and the questionnaire application are served on Vercel\footnote{\url{https://vercel.com}.}, the FastAPI service runs on Render\footnote{\url{https://render.com}.}, and the database is a managed PostgreSQL instance on Neon\footnote{\url{https://neon.tech}.}; the \texttt{docker-compose} configuration in the repository provides an equivalent stack for local development. Client and service exchange JSON over two paths, plan persistence and read-only consultation, and the service's own structure is the subject of Figure~\ref{fig:impl-backend-components}.

\label{sec:impl-frontend}

\paragraph{Feature Modules}
At the top, the client is divided by feature rather than by technical kind. Each of the profile, the catalogue, the Dashboard, the Recommendation Panel, the onboarding tour, the prebuilt plans, the compliance feedback and the planning canvas is a module holding its own state, its own effects and the components that render it; the screen is assembled from them. A module may depend on the layer beneath it and on no other module, so a change to one feature cannot reach another except through the plan they share.

\paragraph{The Domain Layer}
The domain layer holds the rules for terms and lanes, which decide the season a lane carries and whether a course may be offered in it; the lane geometry that turns a drop position into a semester; the graph's filter matching, which keeps a matched course's whole ancestry on screen; the builders behind the prebuilt plans; and, at its centre, the plan and the reducer that changes it. All of it lives there on the terms the figure states: it imports no framework, so neither React nor React Flow; touches no browser object; and makes no request. Each part is therefore exercised by calling it.

That plan is what a student builds and what everything else in the tool reads: the courses filed under each semester, the codes marked done and the codes parked, the notes, hour estimates and grades on individual courses, the note on each semester, the chosen focus area, the workload limits, and what the graph remembers between visits, its filters, its collapsed nodes and the positions nodes have been dragged to. One such plan is held for each programme a student has opened, and the account holds the set of them. The Graph View and the Table View are two projections of that plan: switching view changes how the plan is drawn, never which plan is described, and persistence, the Dashboard, compliance feedback and recommendations are all derived from the same model.

The reducer is a pure function from the current plan and a described change to the next plan; marking a course complete, applying a prebuilt plan, switching programme, choosing a focus area and clearing the plan are dispatched to it as discrete changes, each exercisable by calling it rather than by rendering the interface around it.

Placing, moving and parking a course in the Table View are handled differently. The board's node array is built from the plan when a programme is opened, and on every commit the array is written back whole rather than as a single described move, because one interaction rarely moves one card: collision spacing, module group clearance and the relocation of courses stranded by a change of start term shift others at the same time, and writing the array back captures all of them at once. The canvas is therefore an input to the plan and not only a rendering of it.

The Graph View does not take part in this. Its node positions encode curriculum depth and subject band, so dragging there changes a remembered offset and nothing else. Adding a course from the graph does reach the plan through the same array, but its lane is named by the \gterm{semester-picker}{Semester Picker} (Section~\ref{sec:semester-picker}) rather than read from where a card was dropped.

\paragraph{The API Client}
A single foundational network module encapsulates all client-service communication via fourteen explicit request functions (handling authentication, catalogue data, plan persistence, profile settings, compliance, and recommendations). By restricting all network connections exclusively to this module, the architecture enforces strict layering. Additionally, the module localizes all transport-level configurations (such as service endpoints, bearer tokens, and payload structures), ensuring the upper application layers remain entirely agnostic to the network implementation.

\subsection{How an Edit Travels}
State mutations follow a strict unidirectional data flow (Figure~\ref{fig:impl-edit-flow}). While standard UI inputs (such as the Semester Picker or text fields) dispatch discrete actions, Table View drags introduce an architectural exception. As established, drag interactions return the updated node array, mapping horizontal coordinates to planned semesters. Consequently, this is the single instance where the canvas acts as a direct state input rather than a pure rendering layer.

Once an action or drag is processed by the plan reducer, the resulting state update triggers two independent execution paths. Synchronously, pure layout functions recalculate affected graph columns or table lanes to trigger a view re-render. Asynchronously, the updated plan is persisted to the backend, while the compliance and recommendation endpoints are queried to update the Dashboard and transient feedback banners. Network persistence is debounced by 500 milliseconds to prevent excessive writes during exploratory interactions. While API consultations are not debounced, they mitigate race conditions via request identifiers: stale responses arriving after a subsequent edit are explicitly discarded rather than applied out of order.

Finally, the course lifecycle (Section~\ref{sec:lifecycle}) requires no dedicated state-machine controller. Course states are handled declaratively within the plan, transitions are managed entirely by the reducer, and valid action buttons are derived dynamically at render time. Graph visibility is computed similarly: a self-contained module evaluates courses against active filters and preserves every ancestor of a match, so a matched course is never hidden because its module or exam subject was filtered out (Section~\ref{sec:graph-spatial}).

\section{Backend}
\label{sec:impl-backend}

The backend service provides three functions: persistence of the study plan, curriculum compliance evaluation, and course recommendation. It is a FastAPI application structured in four layers with a strictly downward dependency direction (Figure~\ref{fig:impl-backend-components}). Request handlers validate input, invoke exactly one use case, and serialise the response; they contain no domain logic and no SQL. Use cases orchestrate domain operations and define the transaction boundary; they cover authentication and sessions, catalogue retrieval, prerequisite relations, plan persistence, profile settings, compliance evaluation and recommendation. The third layer consists of two rule packages, compliance and recommendation, described in Sections~\ref{sec:impl-compliance} and~\ref{sec:impl-recommender}. Repositories encapsulate all SQL statements.

Use cases access storage exclusively through a unit-of-work abstraction: an object that provides every repository bound to a single database connection. A use case therefore neither acquires connections nor references concrete repository classes. Two properties follow: a use case can be tested against a substitute unit of work without a database, and the set of statements that must commit atomically is declared in the use case rather than determined by repository execution order. Domain failures are raised as typed exceptions named for their cause, for instance \texttt{ProgrammeLocked}, \texttt{StartTermLocked} and \texttt{SetupIncomplete}; a single mapping table translates exception types to HTTP status codes and is the only component of the service aware of HTTP semantics. Authentication resolves the user from a session token supplied either as a cookie or as a bearer token, so that the deployed and the local client authenticate against an unchanged service. Persistence uses a shared PostgreSQL connection pool with parameterised SQL; no object-relational mapper is employed.

\subsection{Curriculum Compliance Engine}
\label{sec:impl-compliance}
The Compliance Engine (implementing Feature~\ref{feat:003} and Feature~\ref{feat:005}) enforces rules derived exclusively from the published curricula of the two supported programmes: the Bachelor in Computer Science and the Master in Software Engineering\footnote{\url{https://informatics.tuwien.ac.at/bachelor/curriculum-ue033521.pdf}, \url{https://informatics.tuwien.ac.at/master/curriculum-ue066937.pdf}; the versions in force during this work were used.}.

The architecture strictly separates curriculum data from evaluation logic. Programme regulations are encoded in distinct JSON configurations loaded at construction, ensuring curriculum revisions require only data updates. Because the curricula structurally diverge (for example, the Bachelor requires an introductory phase, the \emph{Studieneingangs- und Orientierungsphase} (\gterm{steop}{StEOP}), whereas the Master enforces prerequisite pairs), they share neither a JSON schema nor a common validation base class. Forcing a shared inheritance model would introduce premature architectural abstraction; instead, evaluation relies on programme-specific rule sets dynamically selected via programme code.

During evaluation, the engine computes credit totals against curriculum constraints (such as load ceilings, module completeness, and prerequisite sequencing). To guide rather than block users (Section~\ref{sec:overall-scope}), findings follow a two-tier severity model. Critical violations (like broken hard prerequisites) trigger errors that revert the client's action, whereas soft violations (like suboptimal elective sequencing) trigger advisory warnings. A rejection message is built from the triggering change: it names the action and the course code, in the Master rule set also the target semester where the change carries one, followed by the first rule that failed. Finally, the evaluation payload includes all aggregate statistics required by the Dashboard, establishing the engine as the single source of truth for both UI rendering and the internal recommender system (Section~\ref{sec:impl-recommender}).

\subsection{Recommendation Support}
\label{sec:impl-recommender}

The recommendation engine (implementing Feature~\ref{feat:007} and Feature~\ref{feat:012}) is designed strictly to evaluate the user experience of explainable recommendations, explicitly excluding algorithmic accuracy from the research scope (OOS5). The architecture employs a hybrid ensemble approach, combining content-based matching, rule-based sequence relations~\cite{wong_sequence_2018}, and collaborative filtering~\cite{bhumichitr_recommender_2017}. Because no record of prior students' plans was available, the collaborative components query a synthetic dataset of prior student plans. Consequently, the engine serves as a functional prototype that simulates data-driven UI behaviours for the evaluation study, rather than a contribution to core recommender-systems research.

The system is structured as a federated pipeline of six scoring \gterm{recommendation-channel}{channels} (Interest, Similarity, Sequence, Follow-on, Peer, and Internship). Two of them could not fire against the study's data: the Sequence and Follow-on channels drew on a hand-written knowledge graph that named courses present in neither catalogue, so four channels were live in the sessions Chapter~\ref{chap:evaluation} reports. Both were repaired afterwards, and no participant saw them working. Each adheres to a common interface, returning a numerical score and an explainable evidence string for a candidate course (Figure~\ref{fig:impl-shot-recs}). The channels employ distinct heuristics. For example, the Interest and Internship channels use weighted keyword matching, the Similarity channel surfaces curated catalogue links, and the Follow-on and Peer channels calculate probabilistic overlap against the synthetic cohort (Peer reverting to global popularity for an empty plan). After aggregating and deduplicating, the results are sorted by score, a relevance value in $[0,1]$ that each channel assigns on its own scale. The top 100 candidates are then passed to the Compliance Engine for trial placement, and any course that would introduce an error or a warning not already present in the plan is discarded. At most 15 recommendations are returned. All six channels were active during the sessions reported in Chapter~\ref{chap:evaluation}; the four that depend on the student's profile or on the cohort return nothing without input, so what a participant saw varied with what they had entered.

\section{Data Model}
\label{sec:impl-data}

The database models a study programme as a strict four-level hierarchy (Figure~\ref{fig:impl-data-model}): programme, exam subject, module, and course. While the seeded data guarantees a strict one-to-many relationship between modules and courses, this constraint is not explicitly enforced at the schema level. To optimize network retrieval, a materialised view projects the catalogue of each programme into a single nested JSON document. Upon request, the backend dynamically merges the user's term-availability overrides into this payload, ensuring that the globally shared catalogue data remains strictly immutable. Evolving or non-relational course metadata (such as content descriptors and curated similarities) is encapsulated within a schema-less \texttt{JSONB} column.

User-specific state comprises an account record, a single persisted study plan, and a profile per programme. The plan table enforces a 1:1 user-to-plan cardinality via atomic upsert operations. The profile table, however, uses a composite key of user and programme, allowing students to retain distinct configuration profiles when switching curricula. Crucially, the schema enforces loose coupling between user state and the catalogue: plans reference courses via natural identifiers (course codes) rather than surrogate foreign keys. This decoupled architecture ensures user plans remain valid when the catalogue is reseeded.

\section{Evaluation Instrument}
\label{sec:impl-userstudy}

The evaluation sessions (Chapter~\ref{chap:evaluation}) were run with a small, standalone questionnaire web application, kept deliberately separate from the study planner so that instrumentation could not affect the tool under study. It guides a session through consent, demographics, the task scenarios, and the post-task questionnaire, keeps its own timers, and submits each session's responses for later analysis. The instruments themselves and the study they support are described in Chapter~\ref{chap:evaluation}; the application is noted here only as a distinct artefact produced for this work.

\section{Verification}
\label{sec:impl-verification}

Munzner's nested model assigns specific threats to validity, and corresponding validation methods, to each of its four levels. The model warns of cascading errors: a failure at an inner level can invalidate outcomes at an outer level~\cite[p.~922]{munzner2009}. This chapter operates at the algorithm level. Verifying technical correctness here is essential to ensure that the subsequent user evaluation (Chapter~\ref{chap:evaluation}) measures genuine design efficacy rather than underlying software defects. Verification prioritises the Compliance Engine, as both user trust and the evaluation findings depend entirely on its accuracy. The system is validated across three testing tiers:

First, a deterministic snapshot-testing strategy captures the engine's exact output across 38 distinct scenarios for both programmes, covering boundary conditions, empty plans, and deliberate rule violations. Every verdict and aggregate statistic is compared field-by-field. To prevent false positives from uniform data, the test corpus enforces structural deduplication: the corpus builder refuses to record any scenario set whose answers are less than half distinct. This exact snapshot strategy is mirrored for the recommendation engine across 85 distinct profile and channel configurations. 
Second, API contract tests assert that endpoint status codes and response schemas remain stable across revisions, employing data sanitisation to isolate dynamic values such as timestamps and database identifiers. Third, end-to-end tests drive a browser environment against the running stack to simulate the core planning loop. This tier is necessary to verify the bidirectional state reconciliation between the underlying plan model and the UI canvas (Section~\ref{sec:impl-frontend}), which cannot be observed outside a real rendering context. Standard unit tests isolate the remaining domain logic, including the plan reducer, graph filters, curriculum configurations, and database migrations. Because the core state model is a pure function and the Compliance Engine is deterministic, this snapshot-heavy verification strategy yields stable outputs. A continuous integration pipeline enforces this entire suite, alongside strict static type checking, on every codebase modification.

\section{Revisions After the Evaluation Study}
\label{sec:impl-post-study}

Everything described up to this point is the system used in the evaluation study of Chapter~\ref{chap:evaluation}. This section records what was changed afterwards, and it is kept separate for exactly that reason: none of it was in front of a participant, and no finding in Chapter~\ref{chap:evaluation} may be read as evidence about it. What it records is the set of defects the study surfaced that have since been closed, and one addition stated with them (Section~\ref{sec:impl-post-study-fixes}).

\subsection{Corrections to Reported Defects}
\label{sec:impl-post-study-fixes}

The defects of Table~\ref{tab:problems} are held as a register in the tool's repository, ranked by the severity and frequency reported in Chapter~\ref{chap:evaluation}. Seven have been closed, each with a regression test that reproduces the observed failure before the fix and passes after it. The remainder are open. Four of the seven appear in Table~\ref{tab:problems}; the other three are recorded in the full codebook (Appendix~\ref{app:eval-codebook}) below that table's threshold, and are closed here because each was a small change with an unambiguous correction rather than because the study ranked them highly.

\begin{itemize}
    \item \textbf{The season of each semester lane (E-P29, 3, 11/11).} The lanes alternate between winter and summer from the student's start term, and a season-locked course fits only half of them; the tool held both halves of that comparison and drew one, the course's own term on its card and in the catalogue. The lane now carries its season in the same notation, so the comparison is read rather than counted out.
    \item \textbf{Feedback banners (E-P50, 2, 9/9).} One visual style carried acceptance, rejection and progress, so a refusal could not be told from a confirmation; the three are now distinct and a rejection names the constraint that produced it. Separately, the completion percentage was measured against a credit total written into the client, which is what produced the runs announcing 25\,\% completion at 102 and at 108 of 180~ECTS; it now comes from the curriculum in force, reported by the rule engine, and a plan that crosses several milestones at once announces the highest rather than the first.
    \item \textbf{The empty recommendation panel (E-P42, 1, 4/11).} A channel that returned nothing rendered a bare dead end. The panel now distinguishes the cases it can tell apart: every source switched off, a switched-off source that does have candidates, a profile that states no interests for the channels to match against, and sources that are live but returned nothing for this plan. This does not repair the underlying cause, the placeholder interaction data of Section~\ref{sec:impl-recommender}; it stops the empty state from reading as a fault in the tool.
    \item \textbf{Study wording in the production interface (E-P27, 1, 10/11).} The profile and the sign-up form both carried a \enquote{Disable Graph View} checkbox written for the study's baseline condition. The option is removed rather than reworded, together with the per-user flag it set: the graph is now always reachable, and the onboarding tour no longer has a reduced variant. This also closes E-P13 (1, 1/11), which recorded the checkbox's negative phrasing as easy to misread.
    \item \textbf{The milestone banner's arithmetic (E-P54, 2, 6/10).} The banner reported the lowest milestone a change crossed while printing its own ECTS figures beside it, so a plan loading from empty announced 25\,\% completion at 102 of 180. It now names the highest milestone crossed.
    \item \textbf{The programme a new account opens in (E-P09, 1, 11/11).} Every account opened in the Master programme, whatever the student intended, and was corrected only after the first profile request had already been issued for the wrong one. The planner now reads the student's own programme before the board is built.
    \item \textbf{Failed sign-in and sign-up (E-P41, 1, 1/11).} The form printed the transport, status line and response body included. Each failure now names the problem and the next step, and no message repeats the server's own wording.
\end{itemize}

One change was an addition rather than a correction. The overlay of the evaluated graph drew only the orderings the Compliance Engine blocks on, which the Master curriculum has two of and the Bachelor none, so the programme the study planned in carried no prerequisite edge at all. The same switch now draws the advisory orderings beside them, dashed and labelled \emph{recommended before} where the enforced ones are solid and read \emph{required before}, so an edge states not only that an ordering exists but what breaking it costs: a refusal in the Master's case, a Dashboard warning in the Bachelor's. The pairs themselves are unchanged, two in each programme, and are the same copy the checkers read (Section~\ref{sec:impl-compliance}); the expected prior knowledge the curricula additionally state per module is not drawn, because it carries no consequence the student could act on. No participant saw the advisory edges, so Chapter~\ref{chap:evaluation} carries no evidence about how they are read, and the code that asked for ordering at the point of placement is not answered by them: two edges in a view the student does not place in are not the indicator those four participants described (E-P44, 4/11).

\section{Key Decisions}
\label{sec:impl-decisions}
Three implementation decisions bound what the evaluation could observe. Each is stated with its rationale, its cost, and its consequence for Chapter~\ref{chap:evaluation}.
\begin{itemize}
    \item \textbf{Single Plan, Two Projections:} Both views render one plan model and neither owns it (Section~\ref{sec:impl-frontend}). The cost is that all UI-specific state must be structurally hoisted into the shared, persisted plan document, thereby coupling transient view logic to the global data model. In return, the manipulation between the two conditions of the evaluation study was confined to one surface: the plan model, the compliance feedback and the recommendations were identical in both.
    \item \textbf{One rule set per programme, no shared engine.} The two rule sets share only the request format, the result schema, the entry point and the handling of credit limits (Section~\ref{sec:impl-compliance}); no engine parameterised by curriculum was built. The rationale is that the two curricula share almost no rule, so a common core would have been smaller than the abstraction needed to express it, and the simpler structure sufficed for the purpose. The cost is that a third programme requires a third rule set and so on. The study is unaffected: only the Bachelor rule set ran in the sessions.
    \item \textbf{Recommendation data quality.} The content-based and sequence channels run on the catalogue's course content, its curated course similarities and the curricula's orderings, and on the student's own profile; the two behavioural channels run on a synthetic cohort (Section~\ref{sec:impl-recommender}). The consequence is that the evaluation observes how students treat an explainable suggestion, not how good the suggestions are.
\end{itemize}
